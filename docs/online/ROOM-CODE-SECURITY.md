# Room code security

Room codes are six uppercase letters or digits, sampled uniformly from 36⁶ = 2,176,782,336 possibilities (31.02 bits). They are the join capability: anyone who learns a code can attempt to join. Six characters remain manually typable; letters and digits can be mistaken for one another, so copying an invite link is preferable. Rejection sampling removes modulo bias. Code allocation still uses a transactional reservation.

The admission budget charges 30 failed guesses per address per hour across instances, subject to the admission gate's availability and concurrency limits. At exactly 30 guesses per hour, a complete sweep takes about 8,283 years per address; with N independent addresses the idealized time is divided by N, and a random guess has probability `live rooms / 36⁶` of hitting any live room. These estimates are not a guarantee against distributed guessing, leaked codes or compromised members.

The ICE and end routes return the same 404 body for a missing room and a caller lacking membership or host authority. Each endpoint has a separate local budget per address and instance: burst 12, then 30 requests per hour. This permits twelve devices at a shared address to fetch ICE together; under heavier use ICE clients fall back to the standard STUN configuration. These limits are not global and scale with the number of instances.

For cross-instance detection, the server emits `room-lookup-misses` structured log records with `count: 30` for every 30 refused lookups per instance, with no room codes or addresses. Configure a log-based counter summing `count` across instances and alert on its rate; that external monitoring configuration is not created by this change. A partially filled batch can be lost on instance shutdown, so this is a lower bound, not an exact global count. Budget refusals do not produce miss records or database reads. Logging is bounded to one record per 30 misses, avoiding one log write per attack request. Automatic per-room lockout is deliberately omitted: unauthenticated guesses could otherwise terminate or lock an honest room. Investigate aggregate spikes and use edge controls as needed.

This changes the protocol: old cached clients only understand four-character codes, and existing four-character rooms cannot be joined or managed through the new endpoints. Coordinate frontend and backend rollout, prompt users to reload, and expect active old rooms to end; there is no rolling compatibility guarantee. Do not deploy until the rollout and interruption are accepted.
